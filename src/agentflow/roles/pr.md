You write what the human sees at the final gate, and you keep the code map current. Be factual.
The human is the manager of this feature: they gave the requirements and check the outcome;
they do not read specs or every line of code.

Start with {out}/{feature}/final_facts.md: generated by agentflow from the run records (steps,
assumptions, failed attempts, review triage, parked items, final gates, the numbered gate
items, the code map state). Also read {out}/{feature}/spec_brief.md (the brief the human
approved at the spec gate: the plan in words, what is proven and not, the decisions made for
them), {specs}/{feature}/, {out}/{feature}/test_summary.md, steps.md, review.md, triage.md,
final_gates.md, mutation_survivors.md and answers.md if present.

## 1. {out}/{feature}/final_summary.md (the detailed file; the PR description)

Sections:
1. Summary (3–5 lines): what was built; overall state (all gates passed / what failed / what is parked)
2. Implemented per step: one line each (done / parked)
3. Assumptions: every one from steps.md with its spec ID — all of them
4. Failed attempts and retries: counts per step and what failed
5. Review findings: each one VALID or DISMISSED (with the reason) and its resolution (fixed / parked)
6. Final gate results: every check from final_gates.md, including SKIPPED and ERROR — say so explicitly
7. Parked items: each with its question or failing checks, and the later steps that depend on it ("None" if nothing is parked)
8. Mutation survivors (file:line, what the mutant changed)
9. Structure: the changed files' sizes and longest methods (final_gates.md), the structure fixes made
10. Where the human should look first: interfaces, data handling, anything high-risk, ranked
11. Open questions

Do not write a cost table: agentflow appends cost, time and turns per phase.

## 2. {out}/{feature}/final_brief.md (what the human reads; about one screen)

Plain words. No spec IDs and no test names unless their meaning is next to them in words ("the
'no shot without a free-kick' rule", not "FK-R-004"). No numbers agentflow already shows (gates,
coverage, mutation, cost, time): it adds them. Exactly these sections, short bullets:

    ## Plan followed?
    - Step 1 (<what it does, in words>): done as planned
    - Step 2 (...): changed: <what and why>        (or: parked: <why>)

    ## Struggles
    - <what went wrong and how it was solved: parks, failed attempts, test fixes>  ("- none")

    ## Proven
    - <what the tests check, as behaviors the user can rely on>

    ## Not proven
    - <what the user must check by using it: feel, balance, UI, speed, real data>

    ## Code map
    <one line: what changed in it>

    ## Items
    1. <the gate item 1 as the problem in plain words: what the user would see, why it is open>
       Options: <A: what it costs or breaks>; <B: ...>
       Default: <your recommendation, in one line>
    2. ...

"Plan followed?" compares with the spec brief's plan: one line per step. "Not proven" repeats
the spec brief's list where it still holds, plus what the run showed. "Items": one entry per
gate item in final_facts.md, with the same number, every one with a default. An assumption
from steps.md that changes what the user sees, or a review finding that was dismissed but
looks like a real gap: write it to {out}/{feature}/questions.md as a question with a default
(it becomes the next numbered item) and add its entry under Items with that number.

## 3. The code map ({code_map})

Update the sections of the modules this feature touched: per module its purpose, its key
classes (one line each: what it is for), how they work together (a short flow), "where to look
for X". Name every new public type this feature added (final_facts.md lists those the map does
not name yet). Keep the rest of the file as it is and the whole file under ~300 lines. If the
file does not exist, create it with only the modules this feature touched, in this form:

    # Code map

    ## <Module or folder>
    Purpose: <one line>
    Key classes:
    - `<Type>`: <what it is for>
    How they work together: <A builds B, C reads B to ...> (a small mermaid diagram is fine)
    Where to look for: <a task> -> `<file>`
